# 九领域架构与一致性

网关与九个业务服务独立运行。user、hotel、inventory 沿用上一阶段独立数据所有权；原 business 已撤销，拆为 order、marketing、payment、stay、review、statistics。网关保留原浏览器 API 路径。

## 数据与调用

订单服务唯一拥有 booking_order、booking_guest、booking_request；保留管理查询和 AI 推荐的 API 聚合，聚合通过用户/酒店/库存/营销/评分接口取数。其他领域不更新订单主表。payment/stay 的 order_snapshot 用于本地操作和列表，执行关键操作前由订单所有者锁定后返回当前快照。

评价拥有 order_review，创建时查询订单所有者确认顾客归属和已退房状态，记录订单号和房型快照，审核不依赖跨库 JOIN。营销拥有促销、每日优惠、签到、券及 marketing_reservation；日优惠额度以本服务有效预留为准，不查询订单主库。

支付拥有支付、退款申请和退款流水；入住拥有实体客房、分配、房态历史、办理记录和 stay_charge。续住费用先作为入住事务的唯一费用意图保存，再由支付服务幂等生成账本记录。统计消费订单、支付及办理事件维护自己的读模型，接收方停机不阻止业务主事务。

九个账号只获本域必要表的 SELECT/INSERT/UPDATE/DELETE，没有建表和跨域查询权限。投影是本地可重建副本，不形成跨域数据库外键；员工、顾客等外部 ID 保留，界面名称通过用户目录查询。

## 预留与工作流

下单先持久记录营销交接意图，再调用营销 Try；券和优惠额度在营销本地事务占用，重复操作 ID 校验完整请求。订单提交后 Confirm，回滚 Cancel；Cancel 先到会留下墓碑，防止迟到 Try 重新占用。订单进程中断后，恢复任务使用订单唯一索引和 NOWAIT 锁核对事实，数据库不可达或行锁未释放时保持 UNKNOWN。库存继续采用已有 TCC 与缓存修复协议。

支付、退款、入住、续住、退房和完成采用订单工作流：本地域 INTENT → 订单 ACTIVE 占用 → 本地域 COMMITTED（业务记录+结果+完成消息+Outbox 同事务）→ 订单 COMPLETED → 本地域 DELIVERED。业务失败经过 ABORTING/ABORTED 释放占用，取消先到会保留墓碑。订单只接受授权动作的字段和状态变化，库存副作用须符合动作，续住日期、晚数及金额增量需一致。已提交的本地域操作不能因通信失败被当成未发生。

工作流重复请求校验动作、订单与请求摘要。完成请求响应丢失时，订单端重复完成直接返回成功；本地域只回放已保存结果，避免新增支付和入住记录。未决操作通过前端“处理中”和运维状态显示，阻止订单取消/超时覆盖。恢复任务依据持久日志重试，没有用内存任务替代恢复依据。

## 事件可靠性

DomainTransactionAspect 在服务本地事务边界捕获显式所属表的变化，与 domain_outbox 一起提交。Outbox 通过带内部凭据的 HTTP 投递；接收方 domain_inbox 校验事件 ID 和内容摘要，projection_revision 对每个来源/实体/ID 串行比较版本。重复、旧版本跳过，删除版本作为墓碑保留，旧事件不能复活删除数据。投影更新、Inbox 和接收后派生业务记录在同一事务。

投递采用至少一次，不声称网络恰好一次；业务结果通过去重和唯一索引保持幂等。连续失败退避到 60 秒，20 次后 DEAD，修复依赖或数据问题后可按来源服务重放。原事件 ID 保留，重放不生成假业务成功。生产事件发布目前比较显式所有者表的事务前后行，适合当前演示数据量；大规模场景应改成逐命令显式领域事件或 CDC，不能将此实现当作已验证的高吞吐方案。

## 演示与排错

`Get-CloudStatus.ps1` 显示健康、事件积压/死信、待决工作流、订单占用和营销交接。`Replay-DomainEvents.ps1 -Domain order` 将该来源 DEAD 事件重新排队；先处理具体依赖/契约错误，再重放并观察状态。容器模式查看各服务日志和内部健康接口，内部端口及令牌不对公网开放。

可演示：支付完成消息暂不可达时，订单显示处理中且拒绝取消；依赖恢复后收敛为已确认且只有一笔付款。统计停机时仍可下单付款，Outbox 保留消息；统计恢复后版本投影补齐，生产者不需要重启。自动脚本仅在隔离环境注入故障。

当前为同实例 schema 隔离，尚未验证跨物理数据库部署、高并发容量或多副本高可用。内部令牌是受信内网凭据，不等同于零信任服务身份；生产环境还需网络隔离、服务身份和密钥轮换。
