# 微服务迁移说明

> 当前交付架构与验收见 [delivery-status.md](delivery-status.md)，本文保留阶段历史。当前已完成用户、酒店、库存四 schema 隔离；订单核心边界与剩余职责见 [订单边界说明](order-service-boundary.md)。

## 已落地

1. Maven 父工程统一版本，五个独立可执行 Spring Boot 应用，公共类库和独立前端。
2. 用户控制器和实现真实迁出业务进程，管理支付列表从原 AdminAccountController 单独归入业务服务。
3. 网关将原路径透明转发，前端不需要同时配置多个后端地址。没有将各进程各复制一份完整单体。
4. 业务服务通过 OpenFeign 调用用户服务的会话校验 API；业务服务不持有 JWT 签名密钥。校验时检查签名、期限、账号状态、凭据版本和当前角色。
5. 修改密码、停用账号、变更角色后旧令牌立即失效。用户服务故障时业务服务返回 503，不降级为信任旧令牌。
6. 内部 API 需要至少 32 字符的独立随机密钥；网关不转发该路径，也不对外开放压测免验证码接口。默认所有 Java 服务绑定 127.0.0.1；Docker 仅发布网关及回环上的数据库开发端口。
7. 清除客户端伪造的身份/内部/代理头，网关使用带认证的客户端 IP 头传给服务，避免所有登录限流都使用网关 IP。服务仍自行认证和检查角色，客户端不能通过 X-User-Role 提权。
8. `nacos` profile 配置服务注册和配置导入；默认无需 Nacos 即可直连启动。应用名与组 `SMARTHOTEL_CLOUD` 一致。
9. 业务服务的账号、顾客归属查询改为用户目录内部 API；删除 SysUserMapper、CustomerMapper、EmployeeMapper、SysRoleMapper、MemberLevelMapper。签到不再 JOIN 账号/顾客表，退款、评价、入住历史列表在本地分页后批量获取名字。
10. 目录契约仅包含账号 ID/用户名、顾客 ID/用户 ID/姓名或角色字典，不传密码、证件号、手机号。每批最多 100 个账号 ID 和 100 个顾客 ID，业务端去重分批。资料服务故障返回 503，没有直接查表的降级路径。

## 明确保留的迁移债务

- 用户与业务已在同一 MySQL 实例上分 schema、分账号；尚未部署到两个独立 MySQL 实例。
- 两个服务各自存储操作日志，历史 AUTH/USER/EMPLOYEE 记录归用户库，其余归业务库。原项目没有统一审计列表接口；后续若增加全局审计查询，应设计聚合或可靠投递，不能恢复跨库直查。
- common 中共享实体和 DTO 较多，用于降低第一步迁移风险；它不是最终稳定的跨服务 API 契约，应随领域抽取缩小。
- 酒店、房价、库存与订单在 business 中继续使用原本的本地事务；没有在本阶段把 `@Transactional` 当成分布式事务。
- 业务节点定时扫描订单并发访问库存的行为沿用原实现，尚未验证多副本调度和集群压测。
- 每次携带令牌的请求进行一次用户服务校验，实时失效语义优先；用户服务是当前认证可用性的依赖点。没有缓存有可能过期的账号权限。
- 内部 HTTP 密钥只用于受控本机/容器网络，跨主机生产部署需 TLS、网络隔离、独立服务身份和密钥轮换。

## 后续拆分顺序与验收标准

1. 用户读取契约、已有数据迁移、跨域外键解除、数据库账号权限隔离已完成；已有 ID 不变。迁移前完整备份及恢复、迁移后新数据回退合并已在隔离库演练。参见 `database-separation.md`。
2. 把房型、房价、可售库存划入酒店服务；订单只保存房型和价格快照，不能跨库 JOIN。
3. 为库存预占建立带 requestId/orderId 的幂等接口、预占记录、到期回收、确认与释放状态机。通过本地事务+outbox/可靠消息和补偿确保订单失败不丢库存、重复消息不重复扣减。
4. 支付退款暂留订单服务，退款的数据库和 Redis 同步也须纳入幂等补偿与重试；不可直接把原事务跨 HTTP 调用拆开。
5. 完成数据库独立后再补 Sentinel、链路追踪、报警及扩容测试；Seata/Kubernetes 不是本阶段的必备启动条件。

每一阶段需通过下单→支付→取消/退款→入住退房回归、旧数据兼容验证、服务故障与重试验证，才能称为完成对应迁移。外部支付宝、AI 没有配置时不会伪造实际调用成功。

## 本阶段验证与启动

`mvn clean verify` 的 clean 很重要：删除源码 Mapper 后必须清除旧 target/classes，防止旧 Mapper 字节码仍被 Spring 扫描。当前交付已进行干净构建，并检查业务 JAR 中没有上述五个 Mapper 类。

70 项测试通过，包括真实 HTTP 目录鉴权、字段最小化、批量边界、资料服务故障拒绝和用户表访问架构约束。实际 Ubuntu MySQL/Redis/Nacos 环境的 16 项回归通过，详见 `verification.md`。

启动命令不变：`scripts/Start-Cloud.ps1 -DependencyHost 192.168.229.131 -Nacos`。当前环境已完成数据库迁移，启动脚本读取自动生成的分库配置。不要重新导入初始化 SQL 或删除数据卷。

## 用户数据库独立（2026-11-11）

用户库包含 sys_role、sys_user、employee、member_level、customer、customer_saved_guest 和本地 operation_log；其他业务表及本地 operation_log 位于业务库。原库保留只读快照。

仅从业务库副本解除指向 customer 的跨域外键，保留域内外键；迁移前后校验订单、优惠券、评价、退款、办理员工等逻辑引用。用户域删除与业务域历史保留仍需通过应用规则协调，不能依赖跨域数据库级联删除。

两个数据库账号只有所属表的 SELECT/INSERT/UPDATE/DELETE 权限，不具备建表或跨域读取权限。数据库结构升级由独立管理流程执行。启动脚本只向各进程传入所需密码，网关不持有数据库密码，JWT 签名密钥仅传给用户服务。


新增酒店查询服务第一步，端口 8083。只读账号读取业务库五张酒店表，库存写事务尚未拆分；当前边界、首次配置和验证见 [酒店查询服务](hotel-read-service.md)。


## 库存本地事务基础（2026-11-11）

库存写入统一经 InventoryCommands，预订 requestId 与订单库存操作均有持久去重记录；库存缓存任务与业务事务同时提交，提交后同步及重试读取数据库最新绝对值。取消不再在事务提交前释放 Redis；超时关单释放失败也有持久恢复点。业务库新增三张表，回退合并已覆盖这些新表。详见 [库存基础与验证](inventory-foundation.md)。远程库存写服务与跨服务补偿仍为下一阶段工作。

## 独立库存写入（2026-11-11）

库存写入和 Redis 投影已迁到 8084 的库存进程；原业务库内库存表由专用账号写入，业务账号仅保留读取原库存表和写业务交接日志的权限。此前本地事务阶段的说明作为历史记录保留。远程协议、已有数据切换与回退边界见 [库存服务说明](inventory-remote.md)。订单和库存尚未物理分库，酒店管理写入仍在业务进程。

## 酒店管理查询与每日售价（2026-11-12）

当前阶段见 [酒店管理说明](hotel-management.md)：管理查询和每日售价由酒店进程实际执行，业务入口保留管理员认证与审计，库存写入维持库存服务，房态与入住订单事务维持原实现。

## 酒店资料查询隔离（2026-11-12）

业务中的酒店资料 Mapper 和入住历史房型 JOIN 已移除，资料读取、区间房价及批量历史名称改为内部调用，并收回业务账号对四张资料表的所有访问权限。当前仍有库存服务的容量读取和业务实体房态/外键关联，未物理分库。具体边界见 [酒店资料查询说明](hotel-catalog.md)。
