# 订单所有权与协调

自本次拆分起，原 smarthotel-business-service 更名并收敛为 smarthotel-order-service。8082 端口保留，Nacos 名改为 smarthotel-order-service，数据库改为 smart_hotel_order。旧业务库保持只读归档，不能用旧快照继续接收新订单。

| 操作 | 本地事实所有者 | 订单侧行为 |
| --- | --- | --- |
| 下单、取消、超时关闭 | order | 营销/库存持久预留与决议，保留请求去重 |
| 付款与退款 | payment | 锁定当前状态、应用允许的付款状态和库存副作用 |
| 入住与退房 | stay | 协调 CHECKED_IN/CHECKED_OUT，办理和客房记录仅在 stay |
| 续住 | stay | 校验新日期/晚数/金额增量与扩展库存指令，更新订单快照 |
| 评价 | review | 内部只读确认归属和订单状态 |
| 优惠券与优惠额度 | marketing | 订单事件驱动核销/释放，独立 TCC 预留 |
| 统计 | statistics | 订单 Outbox 推送本地统计读模型 |

本地事务不跨 HTTP 回滚。关键变更采用持久工作流，订单 active_workflow_id 在未决时禁止取消/关单覆盖。故障返回“已受理、同步恢复中”时应查询原订单，不能将超时解释为没有付款。支付服务保存请求结果，续住账本使用来源操作唯一键，重复调用不重复生成记录。

原库存事务回归夹具仍位于测试源码，生产代码不含直接修改库存主表的旧实现。订单保留房型列表/管理及 AI 推荐的 API 聚合，仅通过服务契约及本地只读投影组合结果。完整协议和边界见 full-domain-architecture.md。

真实支付宝仍要求配置和单独验收；未把 MOCK 和续住模拟流水视为第三方交易。退款库存同步仅在订单所有者确认 REFUNDED 且没有待决协调后标记成功。
